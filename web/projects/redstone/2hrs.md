# Redstone flying machine simulator

- I decided to make a cellular automaton inspired by redstone flying machines in Minecraft. The blocks would be objects that inherit from each other, and every tick the scene is updated and all of the blocks are redrawn in new places.
- I created a class for block, with attributes for x, y, whether it is powered, duplicated of these for what it will be next tick, and an array for tags. I gave it methods to move, update its position, and draw to the canvas.
- I then made a new class Slimeblock, which inherited from it. In Minecraft, slime blocks are sticky, and when they are moved, all of the blocks that touch them are moved too.
- To do this, I gave it a "sticky" tag, and then made a recursive function to find all the blocks connected to it. It gets all the blocks, finds the adjacent ones and adds them to an array, and then checks if any of them are sticky and if so, it finds all the blocks connected to them, and so on. Then when the block is moved, all of these blocks are moved along with it.
- I then tried to add textures and actually draw to the canvas. I imported some textures, and gave the block class a source attribute. It took me a while to work out why it wasn't drawing the images, but I soon realised I had to wait for them to load. I created a function which returned a promise that resolved when the image was loaded, and then used the .then method to only draw the image after that.
- Next I started work on the piston. These would be complicated, and the first issue was that they have a direction. After ostensible research, I found that rotating images was difficult, so I copied some CSS using classes to rotate elements. It didn't work, so I ignored it and moved on to functionality.
- When a piston is powered, it extends, pushing the blocks in front of it. I calculated the relative x and y co-ordinates of the block in front of the piston, and moved the block by that amount.
- I added a tick function to be called every 100ms, but it was taking too long for all the images to load. For now, I instead used a button to update the simulation, and I gave the Block a redraw attribute, which is toggled on if the block has visibly changed state, and only draws if this is true.
- This worked well enough with the few blocks I was testing with, so I moved on to sticky pistons. When a piston retracts, it leaves the blocks behind, but when a sticky piston retracts it pulls them with it, except when it is given a short pulse.
- First I removed the extend() and retract() methods and replaced them with an attribute extended. I also changed the update() method to updatePosition() and updatePower(), so that all pistons could be powered before any blocks or power sources are moved
- After a bit of debugging the piston was finally working. I thought about adding redstone blocks, but then remembered that Minecraft has "hard powering" and "soft powering". When a block is hard powered, it soft powers all the blocks around it, but not if it is itself soft powered, and a component is activated whether it is hard powered or soft powered.
- Once I had supported this, the redstone block would easy, as it was just a normal block that was always hard powered. However I was having trouble with calculating connected blocks, as I had expanded my test build. I don't entirely know what I did to make it work, but the trouble was caused by two adjacent slime blocks trying to move each other and calculate everything else that should move with them.
- In the mean time, I also added a .is() method to the Block. This queries if the blocks tags array includes the given tag, or if it starts with an !, will invert the output. This means I can query if a block can be moved (for example) by using Block.is(!immovable) without having to add an "!immovable" tag to every block that can be moved.
- I tried to make normal blocks push blocks in front of them when moved by a piston, but it was difficult to test, so I instead tried working on the user interface. My plan was to have tools for placing, breaking and powering blocks, the option to save the build to or load it from local storage, and options to run, pause and step through the simulation.
- For the tool selector, I added an event listener for keydown, and listened for 1, 2, 3 or 4 to be selected. I then also listened for up and down arrow keys, which cycle through available blocks. I used a mousemove event listener for finding the position of the mouse, and finally a click event listener which places, breaks and powers the target block depending on the tool.
- I was storing the block classes in an array to try to make it easier to initialise blocks by name, but this was proving more difficult than it was worth, so I undid this and created a function with a switch statement to create a new block based on the name. I also created a function to find the block at the given position, to prevent writing out the filter method every time.
- I then added save/load functionality, which was easier than I expected. I added a method to Block which would export a JSON-compatible object with a block type, x, y and direction, and then wrote a save function which maps the array of blocks to these objects and stores it in local storage. The load function clears all the current blocks, pulls the array from local storage and assembles each block from it.
- I also used event listeners for the page being closed, to save the current build to an "autosave" key, and then load it when the page first loads. The build is also autosaved before loading.
